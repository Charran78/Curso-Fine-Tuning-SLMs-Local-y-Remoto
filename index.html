CAPÍTULO 01

¿Qué es Ollama y por qué Gemma3:4b?

Ollama funciona como el equivalente a Docker para modelos de lenguaje: está escrito en Go, utiliza llama.cpp por debajo y permite descargar, cuantizar, personalizar y servir modelos directamente desde tu ordenador sin depender de servidores externos ni enviar datos privados a la nube.

  • Descarga directa: con ollama pull gemma3:4b obtienes el modelo listo para inferencia local.
  • Servidor API REST integrado: expone el puerto 11434 en localhost para conectar cualquier script en Python, Java o web.
  • Gemma3:4b como base equilibrada: con 4 mil millones de parámetros ocupa ~2.5 GB en cuantización Q4, cabe en cualquier equipo con 4 GB de RAM libre, ofrece ventana de 8k tokens y sigue instrucciones de sistema con fiabilidad.

Qwen3 4B 4B 256K Sí (nativo) Apache 2.0 Soporte nativo de herramientas y contexto gigante
Ministral 3B 3B 128K Sí (nativo) Apache 2.0 Modelo europeo, excelente criterio ante negaciones

CAPÍTULO 02

Anatomía de un Modelfile — El plano de tu modelo

Un Modelfile es el equivalente al Dockerfile: un archivo de texto plano que describe la imagen base, los parámetros de inferencia y la identidad permanente del asistente. Al ejecutar ollama create, Ollama empaqueta esa configuración en un modelo reutilizable.

Directiva / Parámetro Rango típico Función y efecto práctico
FROM <modelo> Obligatorio Define el modelo base del registro (ej. gemma3:4b) o una ruta a un archivo .gguf local.
PARAMETER temperature 0.0 – 2.0 Controla la aleatoriedad: 0.2–0.3 para respuestas factuales/código; 0.8 para creatividad.
PARAMETER top_p 0.0 – 1.0 Nucleus sampling: restringe el muestreo al conjunto mínimo de tokens cuya probabilidad acumula top_p (0.9).
PARAMETER num_ctx 2048 – 32K Ventana de contexto en tokens; aumentarla permite documentos largos pero exige más RAM/VRAM.
PARAMETER repeat_penalty 1.0 – 1.5 Penaliza bucles y repeticiones de tokens (1.1 es un valor seguro).
SYSTEM """...""" Persistente Inyecta rol, idioma, tono y restricciones al principio de toda conversación.
MESSAGE <rol> "..." 2–3 pares Ejemplos few-shot (user / assistant) para fijar formato sin entrenar pesos.
TEMPLATE """...""" Avanzado Define tokens de chat nativos (como <start_of_turn> en Gemma3 o <|im_start|> en Qwen).

              CAPÍTULO 04
              
Más allá del prompt — Fine-tuning vs. Modelfile

            

            
          


          

            El Modelfile equivale a entregar un manual de estilo a un becario: cambia su tono y añade unos pocos ejemplos MESSAGE, pero no altera su conocimiento factual ni evita que alucine cuando desconoce un dominio. El fine-tuning, en cambio, envía al becario a un máster intensivo actualizando sus pesos mediante adaptadores LoRA/QLoRA.
          


          

            SELECTOR DE ESTRATEGIA · ¿MODELFILE O FINE-TUNING?
            

              
              
            

            

              
Recomendación: Modelfile (SYSTEM prompt)

              
Si el modelo ya conoce el tema general y solo necesitas fijar tono, idioma o reglas de respuesta, un buen SYSTEM prompt más temperature 0.2–0.4 es instantáneo y no requiere entrenamiento.

            

          

        


        

          

            

              CAPÍTULO 05
              
El alma del fine-tuning — El Dataset JSONL

            

            
          


          

            En aprendizaje automático rige una regla implacable: basura entra, basura sale. Para modelos de chat como Gemma3 o Qwen2.5/Qwen3 el estándar universal es el archivo .jsonl (una conversación por línea) con la clave messages y roles user y assistant. El script de entrenamiento se encarga después de traducirlo a los tokens nativos (<start_of_turn> en Gemma3).
          

          

            Regla práctica del pipeline slm_automator.py: se requieren al menos 10 ejemplos para activar la división automática 90% entrenamiento / 10% evaluación, aunque 500 ejemplos limpios rinden mejor que 5.000 ruidosos.

              CAPÍTULO 06
              
Fine-tuning con recursos de hormiga (Unsloth + QLoRA)

            

            
          


          

            Gracias a QLoRA (cuantización 4-bit NF4 + doble cuantización) y Unsloth, puedes adaptar modelos de 4B en una GPU doméstica con 6 GB de VRAM o en la GPU T4 gratuita (16 GB) de Google Colab. Solo se entrenan pequeñas matrices LoRA (q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj) manteniendo congelado el modelo base en 4 bits.

Vía B · Entrenamiento remoto con Kaggle (sin GPU local)

              
El módulo experimental kaggle_runner.py, integrado con el pipeline de slm_automator.py, puede enviar un dataset JSONL a Kaggle Notebooks y ejecutar el entrenamiento en una GPU disponible para tu cuenta. La ejecución puede generar model_artifact.zip con el adaptador LoRA y un manifiesto de reproducibilidad. La disponibilidad de GPU T4 y los límites de sesión dependen de Kaggle; compruébalos antes de iniciar.

              
    
                
  • Ventaja: Descarga el adaptador y realiza la inspección, fusión y conversión GGUF en tu equipo, sin depender del tiempo restante del notebook para completar la exportación.
    • 
                
  • Privacidad: La herramienta exige consentimiento explícito y crea el dataset remoto como privado. Comprueba y administra su retención desde Kaggle; no se afirma que se elimine automáticamente tras descargar los artefactos.
    • 
                
  • Reproducibilidad: El manifiesto registra hashes SHA-256 del dataset y la revisión resuelta del modelo base, además de parámetros y métricas del entrenamiento.
    •

              CAPÍTULO 07
              
Integrando el modelo fine-tuneado en Ollama

            

            
          


          

            Ollama no carga adaptadores LoRA sueltos: exige el modelo completo fusionado en formato GGUF (cuantizado normalmente en q4_k_m para equilibrar tamaño y calidad). Puedes exportar directamente con Unsloth o compilar llama.cpp y usar convert.py.
          


          

            
Parche crítico contra el bug #2604 de Unsloth

            
En versiones afectadas de Unsloth, el Modelfile autogenerado tras exportar a GGUF puede apuntar en la línea FROM al archivo pesado en F16 en lugar del cuantizado q4_k_m. El pipeline slm_automator.py reescribe automáticamente la directiva FROM hacia el .gguf cuantizado antes de lanzar ollama create.

          


          

            

              Exportación a GGUF y registro en Ollama
              

                
              

            

            
# 1. Exportar directamente a GGUF cuantizado (q4_k_m) desde Python/Unsloth
model.save_pretrained_gguf("gemma3-4b-fiscal-gguf", tokenizer, quantization_method="q4_k_m")

# Alternativa manual con llama.cpp:
# python convert.py ../gemma3-4b-fiscal-merged/ --outfile ../gemma3-4b-fiscal-q4_k_m.gguf --outtype q4_k_m

              CAPÍTULO 09
              
¿Y si necesito tool calling? Los mejores modelos ≤4B

            

            
          


          

            Gemma3:4b es sólido para instrucción general, pero si tu agente debe invocar APIs o funciones externas con criterio —sabiendo incluso cuándo abstenerse ante negaciones o incertidumbre—, conviene elegir modelos pequeños entrenados específicamente para function calling: Qwen3 4B Instruct (256K tokens, Apache 2.0), Ministral 3B (128K tokens, alternativa europea con gran juicio) y Nemotron-Mini 4B (4K tokens, destilado por NVIDIA, 2.6 GB en Q4_0).
          


          

            

              

                
Ventana de contexto nativa en modelos ≤4B

                UNIDADES: MILES DE TOKENS (K) · MAYOR CONTEXTO PERMITE MÁS DEFINICIONES DE HERRAMIENTAS
              

            

            

              
            

          

          

            
Comparativa orientativa: Gemma 3, Qwen 3 y Ministral

            
Rúbrica didáctica normalizada de 0 (menos favorable) a 5 (más favorable). En VRAM, una puntuación alta significa menor exigencia relativa; en licencia, mayor facilidad/permisividad de uso. Son valoraciones cualitativas para orientar una primera elección, no benchmarks ni propiedades absolutas: dependen de la versión, cuantización, configuración y términos exactos de cada modelo. Comprueba siempre su model card y licencia.

              CAPÍTULO 12
              
Proyecto 3 — Tool calling y agente local con Qwen3 4B

            

            
          


          

            Usando un checkpoint de Qwen3-4B-Instruct ya ajustado sobre 60.000 ejemplos de function calling (hf.co/Manojb/Qwen3-4B-toolcalling-gguf-codex:Q4_K_M, 94% de precisión en selección de función y 96% en extracción de argumentos), definimos las herramientas dentro de etiquetas XML <tools> en el SYSTEM del Modelfile junto a su plantilla <|im_start|>. En Python interceptamos <tool_call>, ejecutamos la función real y devolvemos el resultado al modelo, abriendo la puerta al protocolo estándar MCP (Model Context Protocol).

              CAPÍTULO 13 · CIERRE
              
El futuro de la IA local y el Pipeline Automatizado (SLM Automator)

            

            
          


          

            El recorrido termina donde empezó: con un equipo modesto (incluso un PC de trece años) ejecutando asistentes privados que te pertenecen al 100%, sin cuotas por consulta ni vigilancia de datos. Cuatro tendencias consolidan este camino: modelos de 1–3B con rendimiento de modelos masivos, el fine-tuning como habilidad cotidiana similar a Git o Docker, agentes locales conectados mediante MCP y la exigencia de soberanía y cumplimiento GDPR.
          

          

            Para ejecutar todo este ciclo sin escribir scripts intermedios en cada proyecto, el repositorio Automated-SLM-Fine-Tuning-Tool · rama remote-training (se abre en una pestaña nueva) (licencia Apache 2.0) unifica la clase SLMFineTunerPipeline en slm_automator.py y una interfaz web en NiceGUI (app_ui3.py en localhost:8080).
          


          

          

            
Evolución de eval_loss · Pre-FT / Post-FT

            
Datos ficticios de demostración, no resultados de un entrenamiento real. El baseline Pre-FT se mantiene como referencia visual; los valores Post-FT ilustran una posible curva y no garantizan una mejora.

            

              
            

          


          

            

              
                

                  Paso
                  Método en SLMFineTunerPipeline
                  Acción automatizada
                

              
              
                

                  01
                  load_model_and_tokenizer()
                  Detecta GPU (Unsloth 4-bit NF4) o activa fallback CPU (transformers + peft para Qwen, Llama, Gemma y Phi).
                

                

                  02
                  prepare_dataset()
                  Carga el JSONL, aplica plantilla de chat, valida eos_token y divide en train/eval (si hay ≥10 ejemplos).
                

                

                  03
                  evaluate_model()
                  Evalúa el baseline Pre-FT midiendo eval_loss y respuestas cualitativas a prompts de prueba.
                

                

                  04
                  train()
                  Ejecuta SFT con trl.SFTTrainer ajustando automáticamente bf16 / fp16.
                

                

                  05
                  evaluate_model()
                  Repite la evaluación Post-FT para cuantificar la mejora frente al modelo base.
                

                

                  06
                  export_to_gguf()
                  Fusiona LoRA, cuantiza a q4_k_m / q8_0 (compilando llama-quantize en CPU si hace falta) y parchea el Modelfile (issue #2604).
                

                

                  07
                  register_in_ollama()
                  Ejecuta ollama create en un directorio único por trabajo y limpia archivos temporales pesados.

            Apéndice B · Glosario esencial de IA Local y Fine-Tuning
            

              

                
                  

                    Término
                    Definición práctica
                  

                
                
                  
LoRA / QLoRALow-Rank Adaptation: entrena matrices ligeras manteniendo congelados los pesos base; QLoRA añade cuantización en 4 bits para caber en GPUs modestas.

                  
GGUFFormato binario cuantizado creado por llama.cpp y utilizado de forma nativa por Ollama.

                  
CuantizaciónCompresión numérica de pesos (ej. FP16 a 4 bits como Q4_K_M) que reduce memoria y acelera inferencia con mínima pérdida de calidad.

                  
ModelfilePlano declarativo de Ollama (FROM, PARAMETER, SYSTEM, MESSAGE, TEMPLATE) para empaquetar modelos.

                  
Tool Calling / MCPCapacidad del modelo para emitir llamadas estructuradas a funciones externas y conectarse de forma modular mediante Model Context Protocol.

                  
RAG vs. Fine-TuningRAG recupera documentos externos antes de responder; el fine-tuning internaliza formato, estilo y conocimiento directamente en los pesos.
